# IOJH 2.0 · C05a acceptance record — Customer authentication foundation

**Source of truth:** V5 §§4.3–4.4, 5.13, 7.3–7.6, 13 and 22.6. **Base:** GitHub `main` commit `f2ffa3977e91d7f6c308b170f9c1ac02f36cf234` (inspected 4 November 2026). **Status:** Owner testing required; external Supabase and production build not verified by this deliverable.

## Implemented in this slice

- Independent IOJH Supabase Auth configuration and SSR browser/server clients (publishable key only); optional external config so homepage remains runnable without a Supabase project.
- Next.js 16 proxy retains existing `next-intl` routing while refreshing Auth cookies on account/auth routes. Protected pages separately call `auth.getUser()`; the proxy alone cannot grant access.
- EN/BN sign-in, sign-up, verify-email guidance, password recovery and reset forms; verified-email customer account entry and sign-out. SSR confirmation uses token hash and also supports PKCE code callback. No private data cached intentionally.
- Password reset requires both Supabase Auth user verification and a short-lived HMAC-signed, HttpOnly recovery marker; other signed-in sessions cannot submit a reset through the reset page.
- Zod input schemas, neutral login and recovery error copy, redirect-target allowlisting, accessible form labels, light/dark token-based design, keyboard and reduced-motion baseline.
- Unconfigured state explicitly explains that no real account integration exists. No additional route shell or homepage artwork was changed.
