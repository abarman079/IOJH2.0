# Authorized staging and scheduler setup — NOT automatically activated

## Choice
Supabase Cron + pg_net + Vault is the first staging choice if available in an isolated staging project: one-minute cron schedule, DB-side HTTP dispatch, no always-on Node process, no additional queue vendor. Verify actual Free plan project/extension availability and quotas, pause/resume behavior, cost, network reachability and response retention. Do not assume the existing hosted IOJH development project is staging. cPanel cron is fallback if its actual host enables minute scheduling, supported Node runtime, HTTPS access and process/timeout limits. Managed Vercel Hobby cron is daily rather than minute-level; do not use for this business without plan/terms review. GitHub Actions CI is not a production scheduler.

## Gate 1: probe-only, isolated staging
Deploy exact reviewed SHA to authorized HTTPS staging using separate database and provider configuration. Verify Next.js production server, runtime >=22.12 <25, reverse proxy passes Authorization, POST and no-store, host allows >=40 sec request duration, outbound TLS to Supabase, no shared cache, no redirect/auth wall on narrow runner route, redact headers in access/error logs. Keep all mail/webhook flags false.

Generate dedicated random runner secret locally without printing: in PowerShell `$runnerSecret = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(32)).ToLowerInvariant()` (PowerShell 7/.NET supported; for Windows PowerShell 5.1 use `$bytes = New-Object byte[] 32; $rng = [Security.Cryptography.RandomNumberGenerator]::Create(); $rng.GetBytes($bytes); $rng.Dispose(); $runnerSecret = -join ($bytes | ForEach-Object {$_.ToString('x2')})`). Set private staging environment via owner dashboard; do not log/share. `IOJH_JOBS_RUNNER_ENABLED=true`, `IOJH_JOBS_RUNNER_SECRET=<generated>`, jobs service key for staging only. Mail remains disabled. Restart deployment. For a local manual HTTP check use `Invoke-RestMethod -Method Post -Uri 'https://YOUR-AUTHORIZED-STAGING/api/internal/jobs/run' -Headers @{Authorization="Bearer $runnerSecret"} -ContentType 'application/json' -Body '{}' -TimeoutSec 45`. Output only counts. Do not type real key in command history. Expected 200 and redacted summary; 503 = disabled or backend issue; 401 = invalid key; 405 GET.

In the authorized staging DB only, owner may enqueue one harmless probe with `select public.iojh_jobs_enqueue_probe(gen_random_uuid(), 'c07c-staging-probe-001', null, 3);`. Verify pending before, succeeded after, total_attempts=1 and one completed attempt by joining jobs/outbox on dedupe key. Duplicate runner calls cannot repeat completed probe. Do not use hosted dev for synthetic failure scenarios; disposable tests simulate crashes.

## Gate 2: exactly one scheduler
Check extension availability and permissions in staging (do not install in hosted dev automatically): `select name, installed_version from pg_available_extensions where name in ('pg_cron','pg_net','supabase_vault');`. Owner enables necessary extensions via approved dashboard only. Review `cron.job` names without displaying command text; verify no other invocation of same runner. Use Vault dashboard to store two values named `iojh_c07c_runner_url` (complete HTTPS staging route) and `iojh_c07c_runner_secret` (dedicated secret). Ensure `vault.decrypted_secrets` and `net.http_request_queue` are not readable by anon/authenticated; review all login roles and service access, since pg_net temporarily holds decrypted headers. Never show their contents. If that boundary cannot be secured, use cPanel fallback. No actual secrets in SQL command text. After owner approval execute in authorized staging:

```sql
select cron.schedule('iojh-c07c-staging', '* * * * *', $job$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name='iojh_c07c_runner_url'),
    headers := jsonb_build_object('Content-Type','application/json','Authorization','Bearer ' ||
      (select decrypted_secret from vault.decrypted_secrets where name='iojh_c07c_runner_secret')),
    body := '{}'::jsonb,
    timeout_milliseconds := 40000
  );
$job$);
```

Do not run twice. Confirm job active; cron success means HTTP request queued, not worker success. Review protected Worker health page and pg_net response status only (no headers or body) e.g. `select status_code, timed_out, created from net._http_response order by created desc limit 10;` (verify actual extension schema/columns before querying). Track at least five consecutive minute invocations, oldest due age, successful probe and no unexpected attempts. Compare actual time and host duration against V5. If extension columns differ inspect `information_schema.columns`; no changes to extensions without approval. To stop: `select cron.unschedule('iojh-c07c-staging');`, then disable runner; verify no active duplicate scheduler. Never drop queue.

Fallback: cPanel Cron on verified host, private config outside web root mode 600 and containing `url = "https://AUTHORIZED-STAGING/api/internal/jobs/run"`, `header = "Authorization: Bearer <secret>"`, `request = "POST"`, `header = "Content-Type: application/json"`, `data = "{}"`, `max-time = 40`, `silent`, `show-error`, `fail`. Use cron `* * * * * /usr/bin/curl --config /home/ACCOUNT/private/iojh-runner.curl --output /dev/null` after verifying actual executable and permitted interval; do not put token on cron command line. Protect cron error mail/logs; log only status not headers. Never activate both. Probe-only until proof.

## Gate 3: single real staging email (separate owner approval)
Verify provider project, sending domain, approved sender and recipient, quota (Resend Free advertised 100/day, 3,000/month; confirm current dashboard; Auth SMTP usage may share quota). Create restricted API key privately. No live DNS changes. Do not use `.invalid` test recipient or real customer. In separate approved staging DB, SQL editor owner only, call private atomic `iojh_notifications_enqueue('operational','account_notice','APPROVED-TEST-ADDRESS','en','account_notice',1,'{"reference":"C07C-STAGING-TEST"}'::jsonb,'c07c-staging-mail-001')` once with approved actual address privately; record returned notification UUID. Do not create public RPC for arbitrary recipients. Check one obligation exists and no unexpected active obligations. Configure `IOJH_NOTIFICATIONS_STAGING_ORIGIN` equal to the exact HTTPS staging site origin, `IOJH_NOTIFICATIONS_STAGING_RECIPIENT` approved address, `IOJH_NOTIFICATIONS_STAGING_NOTIFICATION_ID` exact returned UUID, `IOJH_NOTIFICATIONS_RESEND_API_KEY` and `IOJH_NOTIFICATIONS_FROM` privately. Enable `IOJH_NOTIFICATIONS_SEND_ENABLED=true` only after approval; runner already proven. Worker can claim only that notice; subject is labeled STAGING TEST. Verify provider accepted ID, not claimed as delivered. Signed webhook ingestion is separately authorized: configure Resend endpoint `/api/notifications/resend-webhook`, only relevant delivery/bounce/complaint/suppression types, set webhook signing secret privately then enable webhook flag. Validate delivery status with real event and provider dashboard; do not fake signature or send extra real emails for failure tests. Immediately disable send after evidence; keep verified webhook active as appropriate for outstanding delivery events. If ambiguous after timeout, inspect provider records; never change key or notification UUID to force resend. Keep scheduler off until further approval.
